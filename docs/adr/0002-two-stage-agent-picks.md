# ADR 0002：两段式命令，相关性筛选交给 agent

日期：2026-10-04 · 状态：已接受

## 背景

搜索结果里多数条目与目标主题无关。一条内容的加工（下载、转写、纠错）要几十秒到几分钟，
还要花 TikHub 和 LLM 的费用。不筛选就加工，等于把大部分开销花在垃圾上。

纯代码能做的筛选只有字面命中、平台排序、互动量加权，在语义型主题上明显跑偏。
真正的相关性判断需要语言理解。

## 决策

采集拆成两条命令：`topcap search <输入>` 只产出候选清单，不下载任何媒体；
`topcap run <库> --pick 1,3,5` 按序号加工。中间的挑选由调用 CLI 的 agent 完成，
skill 文档规定 agent 必须按主题相关性挑选，不凑数。

不做"一条命令吃关键词直出 md"。

## 理由

- 本项目的主形态就是 agent skill，agent 本身是现成的语义判断器，不需要再接一个 LLM 来筛。
- 候选清单落盘为 JSON，本身是可核查的链路节点：用户能看到 agent 挑了什么、没挑什么。
- 判断归 agent、机械劳动归 CLI，这条缝在整个项目里保持一致：
  CLI 失败不自动补采，长视频闸门也只拦不决定，把选择权交回 agent 和用户。

## 后果

- agent 要跑两条命令；人直接用也多一步。接受。
- 候选序号必须稳定可复现：同一库内 `search` 追加不重排已有序号，否则 agent 记下的
  `--pick 3` 会指向别的内容。
- 博主库的典型需求是"全要"，两段式在这里略显多余，但保持同构比加特例更省认知。
