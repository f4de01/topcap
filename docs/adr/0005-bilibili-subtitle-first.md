# ADR 0005：B站优先使用 CC 字幕，无字幕才转写

日期：2026-10-04 · 状态：已接受

## 背景

B站视频可以有 CC 字幕：UP 主上传的，或平台自动识别生成的。TikHub 提供 `fetch_video_subtitle`
接口返回带时间轴的字幕文本。抖音没有对应接口。

本地转写是整条链路里最重的一步：下载几十兆音频，再跑几十秒模型。

## 决策

B站内容**有字幕就用字幕**拼接成原始文案，跳过下载和转写；没有字幕才走转写。
成稿 frontmatter 记录 `transcript_source: subtitle` 或 `asr`，让读者知道文字从哪来。
不提供"强制转写"开关。

## 理由

- 这是"轻量化"最直接的兑现：B站内容的加工时间从分钟级降到秒级，不占 GPU 和带宽。
- UP 主手工上传的字幕质量通常高于任何 ASR；平台自动字幕的质量与 SenseVoice 相当，
  都要经过同一道纠错。两条路径的产出进入同一个纠错与分段管线，成稿形态完全一致。

## 放弃的东西

- 链路统一性：两条取文案的路径要各自测试。
- 对自动字幕质量的控制：接受，靠 frontmatter 标注让读者自行判断，若某条质量差，
  用户可以删掉成稿后用 `--no-subtitle` 重跑。这是唯一的开关，默认关闭。

## 后果

- 字幕接口的响应结构没有在 TikHub 文档里完整描述，解析代码要对两种形态（直接返回 `body`，
  或返回 `subtitle_url` 需二次请求）都做防御。
- 多 P 视频要逐 P 取字幕，任一 P 没有字幕则整条内容走转写，不混用。
