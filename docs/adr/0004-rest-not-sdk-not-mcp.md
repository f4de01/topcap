# ADR 0004：直接调 TikHub REST，不接官方 SDK，也不接 MCP

日期：2026-10-04 · 状态：已接受

## 背景

TikHub 提供三种接入方式：REST API、官方 Python SDK（PyPI `tikhub`）、MCP server。
本项目只用其中约十个接口：抖音搜索、抖音详情、抖音用户作品、B站搜索、B站详情、B站播放地址、
B站字幕、B站 UP 主作品，加两个链接解析辅助接口。

## 决策

用 httpx 直接调 REST，一个不到 80 行的客户端类，统一做鉴权、退避重试和错误归一。

## 理由

- **SDK**：官方 SDK 覆盖数千个接口，依赖和体积都远超我们的十个调用；其返回结构与 REST 完全一致，
  封装层不带来任何领域价值，却多一个版本耦合点。对一个以轻量为目标的项目，自己写十个 URL 更便宜。
- **MCP**：MCP 是同一套 REST 的 JSON-RPC 包装，多出会话状态（`Mcp-Session-Id`）要维护，
  会话过期或连接假死后要重建。REST 每次请求无状态，超时即重试，这类故障在根上不存在。
  MCP 的价值在于让 agent 直接调工具，但本项目的 agent 调的是 CLI 而不是 TikHub，
  这份价值在这里兑现不了；单个抖音 MCP server 有两百多个 tool，接进 agent 上下文代价也不划算。

## 后果

- 接口路径和响应字段由我们自己维护，TikHub 改字段时要自己跟。接口数少，可接受。
- 若将来要让 agent 绕过 CLI 直接查 TikHub，再重新评估 MCP。
